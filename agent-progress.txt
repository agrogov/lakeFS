### What is wired, and what is only written

Three gaps are code that exists and tests that pass, but no production caller. They are the reason
`docs/iceberg.md` has a "Current limitations" section and §15.4 of the plan has a status table:

1. `pkg/icebergcatalog/files.go` stages a snapshot's files as lakeFS entries, but `commit.go` never
   calls `StageTableFiles`. So table files are not in the GC's view, a diff shows only the pointer,
   and a merge carries only the pointer. §6.3's guarantee is therefore **not** in force yet.
2. `UncommittedGCProtected` (`gc.go`) and `ReservedPrefixProtectPolicy` are implemented and tested,
   but nothing in `pkg/catalog` or the auth bootstrap calls them: the grace window does not filter the
   prepare step, and the `_lakefs_iceberg/` deny is not attached at bootstrap.
3. `NewRemoteSigningService` and `NewCredentialService` have `Routes()` and handlers, but
   `RoutesBuilder` appends only the namespace and table services, so neither endpoint is mounted or
   advertised. `LoadTableResult.config` is empty and clients fall back to their own credentials.

A fourth is a one-line wiring choice rather than missing code: `http.go`'s `newAuthMiddleware` still
builds `api.GenericAuthMiddleware` instead of the catalog's `NewAuthMiddleware`, so
`POST /v1/oauth/tokens` is not served. Basic auth and bearer JWTs work; the client-credentials
exchange that PyIceberg/DuckDB use for `credential=` does not.

## I6-1 (datasets table/namespace items) — implemented

`IcebergEnabled` in pkg/datasets/validate.go reads `iceberg.enabled` (the key pkg/icebergcatalog
uses); disabled keeps the old `(501)` problem, so the service still answers 501. Enabled replaces
it with the §9 shape rules and, in materialize.go, a reserved-item opener that copies

  _lakefs_iceberg/tables/<ns…>/<table>/.pointer     (+ _lakefs_iceberg/files/<uuid>/… for a table)
  _lakefs_iceberg/ns/<ns…>/.namespace               (+ subtree markers/pointers/files for a namespace)

Contract decisions worth carrying forward:
- A reserved item's `target` MUST be its catalog path (`<ns>/<table>` or `<ns>`), because the keys
  are fixed by the repository-wide layout and the dataset must answer `<ds>.<ref>.<ns>.<table>`.
  This also gives the §5.2 rule-3 check the right meaning for these items.
- Namespace markers are owned by namespace items only. Table items never copy them: two sibling
  table items are a valid definition, and both would otherwise claim the same marker key and fail
  the §6.4 merge (regression covered by TestPublishSiblingTableItems).
- A namespace item covers its whole subtree and does not copy ancestors' markers, so attaching it
  together with a table/nested namespace inside it stays an overlap error (one materialisation).
- Multi-level namespaces come from the dotted string in the definition (`.`), matching the lakeFS
  ARN/diff notation; the catalog wire separator is 0x1F. A namespace level containing a dot is
  therefore not expressible — a limitation of the Enterprise-compatible string field.
- Missing table/namespace at the pinned commit → *ValidationError naming the item (400), not 5xx.

Proof that the placement, not just the copy, is right: TestPublishedTableReadableThroughCatalog and
TestPublishNamespaceItem read the published version back with `icebergcatalog.Store.GetTable` /
`GetNamespace`, so the catalog computes the reserved keys itself.

Follow-ups handed to I6-2: api/datasets.yml + pkg/datasets/apigen still say table/namespace are
"answered with 501"; authz SourceObjectArn still checks the whole repository for a table item; and
the docs need the target-equals-catalog-path rule plus the marker-ownership note.

## I6-2 (datasets authz + docs for table items) — done, commit a3c953e63

`SourceReadNode` now special-cases a `table` item: `catalog:ReadTable` + `catalog:ReadTableData`
on `CatalogTableArn(repo, ns, table)` — the pair `/iceberg/api` itself checks — instead of the
`fs:ListObjects`/`fs:ReadObject` pair. A new `SourceTableArn(item) (string, bool)` is the only
builder of that ARN; it answers `false` for a missing or empty descriptor, so the node falls back
to the whole-repository object glob (fail closed). A `namespace` item keeps that fallback: it
covers every table below it, so no single catalog ARN describes it. `fs:ReadRepository` is still
checked first by `CheckSourceRepositories`, and `SourceReader.CheckObject` still authorizes each
entry the materialiser reads, so the catalog pair is not a replacement for SEC-3. `itemSourcePath`
now names reserved items (`<ns>.<table>`, `<ns>`), so a 403 names the catalog object.
